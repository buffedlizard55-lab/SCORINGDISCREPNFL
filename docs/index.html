No revisions were observed in the selected mirror comparisons. The study covers — game-snapshot comparisons across four baselines, not that many unique games. The same games recur across baselines. Zero observed revisions does not prove league records are immutable or eliminate scoring-market risk.

The selected archive pages document post-game player-stat and attribution changes. Examples include yardage adjustments, sack/credit changes and a player line added after a game. These may be relevant to player markets or fantasy scoring if the applicable market and rules existed; the rows alone do not establish an offered line, a scoreboard change or settlement. The sixteen sampled season-weeks do not establish a universal weekly frequency, and the sample is weighted to weeks 1 and 16.

The official feed that used to publish these was switched off in 2026. fantasy.nfl.com/research/statcorrections — the page that carried "official stat corrections as released by the NFL League Office and the official statistician of the NFL, Elias Sports Bureau" — now 302-redirects to a news hub that promotes ESPN as the official fantasy partner. Archived snapshots survive and are what this database is built from, but live alerting can no longer rely on an authoritative feed. See Limitations.

How to read this feed — and what it does not prove
  • A run diffs two snapshots of nflverse/nfldata, a third-party mirror of the NFL's official record. It is not the NFL's own database.
  • An alert is a machine-detected candidate, never a confirmed official correction. Every alert carries verification_status: detected_by_diff_pending_manual_confirmation and actually_changed_outcome: null. The machine detects; a human confirms.
  • A clean run means: no frozen field (score, result, total, overtime) on any already-final game differed between the two snapshots compared. It is not evidence that the NFL issued no corrections in that window — post-game player-stat changes are outside this monitor unless a frozen game-level field also changes.
  • Only rows already final in the older snapshot are compared, and pre-game lines are excluded, so newly-played games and line movement never produce false alerts.
  • Both input SHA-256 hashes are stored per run, so any result can be independently reproduced from the exact bytes that produced it.
  • "Identical inputs" is not the same as "the source did not move." The detector compares a projection (finished games, five frozen scoreboard fields). The manifest beside each snapshot records the SHA-256 of the whole upstream file and the upstream commit it came from, so the feed can show both facts. In every run recorded here the upstream file changed while the frozen projection did not — which is the normal, expected state, and the reason the projection is scoped so tightly.

WatchdogIs the monitor actually running?

A detector that only speaks when it finds something has a failure mode worse than a false positive: it goes quiet. If the schedule is disabled, the runner cannot reach the source, or the comparison throws, the feed simply stops updating and the page keeps looking current. This panel is computed from artefacts that exist independently of the detector's own opinion — the feed, the snapshot store, the delivery log and the published copies — by pipeline/health.py, and it is published by a separate workflow so that a broken detector cannot also break its own watchdog.

What this watchdog cannot see
  • A workflow that GitHub disabled, queued or cancelled — check the Actions history.
  • Whether a delivered notification was read. Slack and Discord webhooks return no read receipt, so a delivery record proves only that the endpoint accepted the payload.

Everyday useGet notified without checking

Three channels, in increasing order of setup. Only the first two need nothing from you.

No setup · no secrets

Atom feeds. Subscribe in any feed reader, browser extension or with curl. Published as static files next to this page, so they work on a fork with no configuration at all.

Comparison feed (Atom) — one entry per completed snapshot comparison, clean runs included.
Corrections database (Atom) — one entry per verified correction row, each linking to its archived official source page. This feed changes only when the database is rebuilt from new evidence; it is not a live wire.

One repository secret

Webhook push. Set ALERT_WEBHOOK_URL (Slack- or Discord-compatible) as a repository secret and the scheduled workflow posts an alert when a candidate change is detected. Off by default so a fork can never spam a third party.

Every attempt is recorded in data/alerts/deliveries.json with an idempotency key, retry count and HTTP outcome. A webhook that exhausts its retries becomes a dead letter and fails the run, so a broken notification path cannot masquerade as a quiet week. The URL itself is never stored — only its host and a SHA-256.

Not shipped · would need a third party

Email / SMS / push to a phone. This project has no mail or SMS provider and will not add one silently: it needs credentials, a sender identity and a compliance story. The honest options are to point a service like an RSS-to-email bridge at the Atom feed above, or to have your chat platform's own mobile app deliver the webhook.

No user accounts, no subscription database and no read receipts exist in this repository. Delivery is at-least-once: an endpoint can accept a message and lose the response, so a retry can duplicate one.

GoalPossible?Blocker

The structural blocker, stated plainly. A differential detector needs the "before" bytes and the "after" bytes. nflverse/nfldata keeps games.csv in Git, so scoreboard vintages exist — that file is scoreboard-only and contains no player statistics. Player statistics are published as release assets that are overwritten in place: the stats_player release was published 2025-07-31, and its stats_player_post_2023.csv asset was created 2026-08-13. No Git-committed player-stat file was found in nfldata, nflverse-data, nflverse-pbp or nflfastR-data.

A player-stat detector can be written and can begin accumulating vintages the day it is switched on, but it can never be validated against the — known historical corrections, because the "before" bytes for those weeks no longer exist on any reachable channel. That is a property of how upstream publishes data, not of our code.

How to reproduce this, and what it does not prove

Run python3 pipeline/run.py churn --commits 2200 --stride 50. It enumerates upstream commits touching data/games.csv, downloads every 50th as a codeload tarball pinned to its commit SHA, and diffs each consecutive pair with the same detect.diff_final_records() the scheduled workflow uses. Every vintage's SHA-256, byte count and download URL are stored in data/evidence/upstream_churn_study.json.

Does not prove: that NFL records never change. It measures a third-party mirror over a sampled window. Sampling is a blind spot by construction — a value changed and changed back inside one interval cannot be observed — and the stride is recorded so the size of that blind spot is known. Zero frozen-field changes over this window is a bounded observation, not a law.

How the engine works, and why it is built this way

Since the legacy corrections feed is retired, the scoreboard workflow keeps its own versioned snapshots of a third-party results mirror and diffs them. Three rules — each one derived from a real bug found by testing against real data — keep the signal clean:

  • Only compare records already final at the older snapshot. A newly completed game is not a post-final revision.
  • Only compare frozen fields — score, result, total, overtime. Volatile pre-game line fields are excluded from the scoreboard comparison.
  • Carry both values and SHA-256 hashes of both inputs, so any alert can be independently reproduced by a third party.

What this project deliberately does not do
  • No fabricated markets or lines. Project-defined stat categories and distance thresholds are review heuristics; they do not prove that any specific market, line or price was offered.
  • No realised-outcome claims. Every record documents potential impact only. A test fails the build if an outcome change is asserted without evidence.
  • No unverifiable anecdote. Widely repeated community reports of corrections flipping fantasy championships are excluded, because they could not be verified to primary-source standard. Their absence is a known gap, not evidence that nothing happened.
  • No inflating the row count. The database is a verified seed, not the full archived corpus. Every row must be regenerable from a stored archived page, so a checkable row always beats a thousand unverifiable ones.
  • No claim of a read receipt. Delivery records prove an endpoint accepted a payload. Nothing in this project can prove a human saw it.
